# Проверки проекта: что чем охраняется

Справочник по всему, что в проекте проверяется автоматически. Заведён на шаге 17, актуализирован
на 2026-09-08 (шаг 44): **932 теста в 41 файле**. «А это где-то тестируется?» имеет точный ответ.

**Чего здесь нет:** правил игры. Что означает бросок, откуда берётся броня и почему трофеи
считаются в машинах — в `wiki/design/`. Здесь только то, КАК это охраняется от поломки.

---

## Как запускать

```bash
cd game

npm run check        # всё сразу: типы + Svelte + линтер + тесты
npm run test         # только Vitest (932 теста)
npm run test:watch   # то же в режиме наблюдения

npm run typecheck    # tsc --noEmit
npm run svelte-check # типы внутри .svelte
npm run lint         # ESLint, он же границы архитектуры

npm run dev          # дев-сервер на 5173
npm run smoke        # сквозная проверка в браузере, нужен запущенный dev
npm run shot         # скриншот дев-сервера
```

Замеры (не проверки, а измерения — см. §5) запускаются отдельно: `npm run sim`, `npm run camp`,
`npm run mapstat`, `npm run galaxy`, `npm run qualitystat`, `npm run mapfair`, `npm run frontstat`,
`npm run econstat`, `npm run supplystat`, `npm run fastcalib`, `npm run boardstat` (масштаб работы на бирже, шаг 44).

## 1. Пять родов проверок, и они разные по смыслу

Их легко перепутать, а ломаются они по-разному и чинятся по-разному.

| Род | Чем | Что ловит | Когда падает |
|---|---|---|---|
| **Модульные тесты** | Vitest, `game/test/*.test.ts` | Неверное правило, потерянное состояние, уехавший детерминизм | Сразу, при каждом `npm run test` |
| **Границы архитектуры** | ESLint, `game/eslint.config.js` | Ядро потянуло за собой показ, `Math.random`, бой узнал о кампании | Сразу, при `npm run lint` |
| **Схемы данных** | Zod, при загрузке JSON | Опечатка в данных: `"damage": "10"` вместо `10` | При старте программы и в `data.test.ts` |
| **Сквозная проверка** | Playwright, `game/scripts/smoke.mjs` | Интерфейс собрался, но не работает: кнопка не нажимается, экран не открывается | Только когда её ГОНЯЮТ (см. предупреждение в §4) |
| **Замеры** | `sim/`, `tools/` | Не поломку, а НЕИНТЕРЕСНОСТЬ: перекос баланса, бесполезное оружие, неиспользуемая ветка экономики | Никогда — их читают глазами |

## 2.1. Шаг 44 подробно: что именно проверяют новые тесты

Шаг 44 поменял устройство биржи — силы противника перестали выводиться из выведенного звена и стали
свойством предложения, — поэтому его проверки стоит знать поимённо.

### `growth.test.ts` — сквозной прогон вместо ручной проверки

Отвечает на вопрос, на который `pnpm camp` не отвечает: **есть ли рост.** Бот-менеджер замера
корабль не покупает и ротой не летает, поэтому лестница проверяется отдельно и командами — так, как
играл бы игрок: биржа → подряд → вылет → бой (быстрым расчётом) → разбор.

| Тест | Что доказывает |
|---|---|
| «стартовой роте есть за что браться, а ротная работа ей не по зубам» | Стартовая ниша цела: работа по силам тройке лёгких находится. И при этом на карте есть работа, которой тройке не поднять, — до шага 44 такой не существовало в принципе |
| «рота с Юнионом берёт работу, которой тройка не видела, и получает за неё больше» | Полный путь: тройка отрабатывает подряд → двенадцать машин → **Юнион куплен настоящей командой** `upgradeDropship` с поиском верфи → находится контракт, посильный роте и непосильный тройке → вылет двенадцатью, поле не меньше 40×40, гонорар кратно больше |
| «ставка сектора бывает только у крупной работы на горячем участке» | Признак `stakes: 'sector'` не раздаётся кому попало: ротный масштаб и выше, наступление или оборона, напряжённость от 0.25 |
| «проигранная оборона сектора отдаёт мир противнику» | Поражение меняет владельца планеты в дельтах и поднимает `frontMoved` с настоящими размерами сторон и потерями из боя |
| «выигранный штурм сектора отдаёт нанимателю соседний мир противника» | Победа двигает флаг соседнего мира под флагом цели; если такого соседа нет — не двигает ничего, и это законный исход |
| «обычная работа флаг не двигает» | Ставка сектора не протекает на рядовые подряды |

Мир для тестов сектора не выдуман: кампания прогоняется на шестьдесят декад настоящим тикером войны
(`advance`), потому что в первый день кампании напряжённость нулевая по всей карте и судьбу секторов
не решает никто.

## 3. Проверки «по ключам»: то, что растёт из данных

Отдельный род, и самый полезный. Общее у них одно: **список проверяемого берётся из ядра или
из данных, а не переписывается в тест руками.** Поэтому новая зона брони, новая причина отказа
или новый биом ломают проверку сами, без того чтобы кто-то вспомнил её дописать.

Их сейчас четыре, и вот они целиком.

### 3.1. Словарь интерфейса — `i18n.test.ts`

Ключи вида `t(\`zone.${id}\`)` собираются в рантайме. Новая зона доедет до экрана молча и
покажется игроку сырым ключом. Тест сверяет словарь с наборами ЯДРА:

- `ZONE_IDS` → `zone.*` и `zone.*Short`;
- `QUALITY_CLASS_IDS` → `quality.*`;
- `MISSION_TYPES`, `OPFOR_TYPES` → `mission.*`, `opfor.*`;
- `BIOME_LIST` (из `data/biomes.json`) → `biome.*`;
- **`CampaignRejectReason` целиком** → `reject.*`. Самый ценный пункт: причин больше сорока,
  они растут каждым шагом, и непереведённая причина показывается игроку прямо в кнопке;
- `MARKET_CLASSES`, `ATMOSPHERES` → `market.class.*`, `starmap.air.*`;
- `WAREHOUSE_ITEM_KINDS` и `WEAR_NODES` → `market.kind.*`;
- `PILOTS.origins` → `origin.*`;
- `GOVERNOR_PRIORITIES`, `FRONT_STANCES`, `WAR_POLICY_KEYS` → `realm.sector.priority.*`, `realm.stance.*`,
  `war.policy.*` (шаг 88);
- `realm.titles` (данные), виды конца найма и исхода требования → `realm.title.name.*`,
  `event.greatRegimentHireEnded.*`, `event.demandAnswered.*` (шаг 89).

Пункт про классы рынка окупился в первый же прогон: названия в словаре были написаны на глаз
(`core`, `frontier`), а в данных лежат другие (`developed`, `agrarian`). Тест поймал это до
того, как игрок увидел бы `market.class.developed` на экране системы.

Плюс грубый обход разметки регулярным выражением по `src/ui/**`: литеральный `t('hangar.fleet')`
с опечаткой не пройдёт. Шаблонные ключи оттуда не вытащить — их и закрывают пять списков выше.

### 3.2. Схемы данных — Zod, `data.test.ts`

Каждая таблица в `game/data/` имеет схему, и схема — единственный источник и валидации, и
TS-типа (`z.infer`). Списки ключей (потоки ГПСЧ, виды работ ремонта, классы исполнения)
выводятся из констант ядра, а не переписываются в схему: второй список тех же имён рано или
поздно разойдётся с первым.

### 3.3. Ссылки вики — `docs.test.ts`

Единственная автоматическая часть синхронизации кода и вики. Ловит битую ссылку на
переименованный раздел и упоминание файла, которого больше нет. Так нашлась ссылка
`#5-класс-исполнения-черновик-ждёт-экономики--m9` — заголовок переименовали, ссылку нет, и она
никуда не вела неизвестно сколько времени.

Чего тест НЕ проверяет и не должен: правду написанного.

### 3.4. Детерминизм — `replay.test.ts`

Golden-replay: сид + журнал команд дают побайтово то же состояние. Ловит уехавший порядок
обхода, случайность мимо `Rng` и любое изменение правил, о котором забыли сказать.

## 4. Сквозная проверка `npm run smoke`

44 проверки в двух актах, обе через настоящий браузер на настоящем дев-сервере.

**Акт I — бой** (заведён шагом 9): интерфейс собрался, карта связна, наведение показывает
клетку и цену хода, щелчок двигает робота, смена режима меняет бюджет MP, бот ходит сам, под
курсором есть разбор целевого числа, профиль линии огня рисуется, генератор перегенерирует карту.
Идёт в песочнице свободного боя — она для того и оставлена отдельным режимом.

**Акт II — цикл кампании** (заведён шагом 17a): основание отряда, ангар (парк и стапели —
разные списки), биржа, подпись контракта, вывод звена, бой по контракту, отход, разбор,
закрытие контракта, возвращение в ангар, прокрутка суток.

**Акт III — остальные экраны** (заведён шагом 17b): казармы (ростер, навыки, найм), рынок
(прилавок, покупка, склад, спред выкупа), звёздная карта (каталог, выбор системы щелчком,
расчёт курса), рота (разбор содержания, сохранение). Проверяется не картинка, а то, что
действие доходит до состояния: найм меняет ростер, покупка — склад и кассу.

> **Предупреждение, оплаченное опытом.** На шаге 17 выяснилось, что смоук был сломан ещё до
> него: он искал кнопку смены фазы по видимому тексту «ФАЗА →», а подписана она по-разному в
> разных фазах («К СТРЕЛЬБЕ →», «СЛЕД. ХОД →»). Проверка висела на таймауте — и никто не знал,
> потому что её не гоняли. **Сквозная проверка, которую не гоняют, деградирует молча.** Отсюда
> два правила: гонять её при закрытии каждого шага, который трогает интерфейс, и **не искать
> элементы по видимому тексту** — только по классам.
>
> Шаг 17b добавил к этому третье правило, тоже оплаченное: **не адресовать элемент номером в
> списке.** Акт II выбирал вкладки через `nth(1)`, навигация выросла с трёх пунктов до семи, и
> проверка молча начала жать «Казармы» вместо «Контрактов». Вкладки теперь несут `data-screen`,
> и смоук ходит по нему.

## 5. Замеры — не проверки

`npm run sim`, `npm run camp`, `mapstat`, `galaxy`, `qualitystat`, `mapfair` ничего не
«проваливают». Они печатают числа, которые читает человек: перекос баланса, оружие, которое
никто не берёт, ветка экономики, в которую никто не заходит.

**Лимит: не больше 1400 боёв за один прогон** (правило пользователя, действует с шага 4,
записано в `CLAUDE.md`). 1400 боёв — около трёх минут, 3000 — около шести, а точности заметно
больше не добавляет. Лимит по итоговым боям, а не по сидам: гоняя оба угла, пиши
`--seeds 1..700`, не `1..1400`.

## 6. Как добавлять проверку

1. **Сначала спроси, какого рода она.** Правило — модульный тест. Граница слоёв — правило
   линтера, а не тест. Форма данных — схема Zod. «Экран не открывается» — смоук.
2. **Список бери из ядра, а не из головы.** Если проверяешь набор (зоны, классы, причины
   отказа), возьми константу — тогда проверка будет расти сама.
3. **Один тест — одно утверждение о поведении.** Название теста — предложение на русском,
   которое читается как факт о правилах: «трофеи с неудержанного поля не предлагаются».
4. **Не тестируй то, что уже держит компилятор.** `noUncheckedIndexedAccess` и строгие типы
   закрывают целый класс проверок бесплатно.
