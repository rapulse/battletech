# game_core.md — платформа и техническое ядро [решено]

Статус: **принятое решение**, не черновик. Этот файл отвечает на вопросы «на чём делаем» и
«как устроено ядро». История того, в каком порядке писался код, — в архиве (§12).

Почему выбран именно этот стек — коротко в [`wiki/decisions.md`](wiki/decisions.md) §1; разбор
альтернатив делался 2026-08-24 (Unity, Python, Rust, Pixi, React, D3).

Игровое содержание (правила, баланс, классификация шасси, глобальный слой) здесь не
обсуждается — оно живёт в [`wiki/design/`](wiki/README.md) и от смены стека не зависит.

## 1. Платформа одной таблицей

| Слой | Выбор | Роль |
|---|---|---|
| Язык | **TypeScript 5, `strict`** | один язык от правил боя до интерфейса |
| Рантайм разработки | **Node 22+**, менеджер пакетов **pnpm** | дев-сервер, тесты, headless-симуляции |

| Валидация данных | **Zod** | схемы JSON-таблиц + выведение TS-типов |
| ГПСЧ | **свой**, ~30 строк | потоки + сериализуемое состояние |
| Поставка | **сайт** (решение 2026-09-02) | десктопная упаковка в Tauri снята: не надо подгонять под платформы, обновления мгновенные |
| Анализ баланса | **Python 3.11** (`venv/bin/python` в корне проекта) + matplotlib | офлайн-тулинг, не рантайм игры |
| Графика | вектор Canvas 2D, палитра одним файлом, CSS-глоу поверх; растр — только стационарные картинки (§11) | без 3D-конвейера |
| Git | обычный git, без LFS | ассеты мелкие, LFS не нужен |

**Внешних зависимостей рантайма ровно одна — Zod.** Всё остальное либо инструмент разработки,
либо написано в проекте. Это осознанная позиция: не заводить абстракцию раньше, чем она
понадобилась.

Целевые платформы запуска — три, одна кодовая база:

1. **Браузер** (`vite dev` / статическая сборка на сервере) — основной режим разработки.
2. **Сайт** — режим поставки. Десктопная упаковка снята 2026-09-02 (`wiki/decisions.md`).
3. **Headless Node** — автобой и батч-прогоны баланса, без отрисовки вообще.

Режим 3 не «дополнительная фича», а следствие правила «ядро ничего не знает о показе». Если
режим 3 сломался — значит, нарушена архитектура, и это ловится тестом, а не глазами.

## 2. Три правила архитектуры

Перенесены из Unity-прототипа один в один: это паттерн, а не C#-код.

1. **`core/` не знает о показе.** Никаких импортов DOM, `window`, Svelte, Canvas.
   Проверяется автоматически (см. §10, ESLint `no-restricted-imports`), а не силой воли.
2. **Состояние меняется только командами.** `Command` → `CommandResult { ok, events }`.
   Рендер проигрывает `events`, ничего не пересчитывает.
3. **Все броски — через один сидированный ГПСЧ.** Бой = сид + журнал команд.
   Отсюда бесплатно: реплей, воспроизводимые баги, автобой, задел под сетевой режим.

Автобой из M10 — не отдельная подсистема, а тот же `core/`, прогнанный с ИИ с обеих сторон без
отрисовки. Поэтому правила 1–3 обязательны с M0, а не добавляются потом.

## 4. Ядро: решения, которые дорого менять потом

### 4.1 Карта — структура массивов, а не массив структур

Клетка — три ортогональных слоя (рельеф × уровень × рёбра), игровая модель в
[`wiki/design/combat/terrain.md`](wiki/design/combat/terrain.md).

```ts
// core/map/HexMap.ts
export class HexMap {
  readonly w: number;
  readonly h: number;
  readonly terrain:   Uint8Array;   // w*h    — TerrainId
  readonly elevation: Int8Array;    // w*h    — уровень; правила ограничивают −5…+5
  readonly objHeight: Uint8Array;   // w*h    — высота объекта поверх клетки (лес 2, здание 1..4)
  readonly edges:     Uint8Array;   // w*h*3  — битовая маска рёбер, направления 0..2
  readonly overlay:   Uint8Array;   // w*h    — дым/пожар/лёд, меняется по ходу боя
  readonly buildings: Building[];   // прочность и тип — только для клеток со зданием
}
```

Почему не `HexCell[]`: снапшот состояния — это `new Uint8Array(terrain)`, мгновенно и дёшево;
хэш состояния для golden-теста считается прямо по байтам; на картах 40×40 из M11 ничего не
меняется.

**Уровень хранится знаковым байтом (−128…+127), а правила ограничивают его −5…+5.** Расширить
диапазон — правка правил, а не переделка формата.

### Рёбра хранятся один раз на две клетки

Ребро принадлежит обеим соседним клеткам. Если хранить по 6 рёбер на клетку, каждое записано
дважды и рано или поздно рассинхронизируется. Поэтому хранятся только направления 0, 1, 2,
а 3, 4, 5 читаются у соседа:

```ts
// core/map/edges.ts
export const RIVER = 1, CLIFF = 2, WALL = 4, GATE = 8, BRIDGE = 16;   // запас до 8 флагов

export function edgeIndex(map: HexMap, hex: Hex, dir: Direction): number {
  if (dir < 3) return hexIndex(map, hex) * 3 + dir;
  const n = neighbor(hex, dir);                  // клетка по ту сторону ребра
  return hexIndex(map, n) * 3 + (dir - 3);       // её «прямое» ребро — то же самое
}
```

Один факт — одно место, теперь и в данных.

### 4.2 Стоимость движения — свойство ребра, не клетки

Единственная ошибка в этом месте, которую тяжело чинить задним числом. По
[`wiki/design/combat/terrain.md`](wiki/design/combat/terrain.md) подъём стоит «+1 за уровень» —
то есть цена зависит от **перехода** `from → to`, а не от целевого гекса. Пасфайндер с сигнатурой
`cost(cell)` высоты не примет, и переписывать придётся и Дейкстру, и подсветку, и ИИ.

```ts
// core/map/movement.ts
export function moveCost(
  map: HexMap, from: Hex, to: Hex, dir: Direction, mode: MoveMode
): MoveStep | null;                // null = переход невозможен

export interface MoveStep {
  mp: number;                      // цена шага
  pilotingCheck: boolean;          // спуск на 2 уровня, бег по пересечённой, переправа
  submerged: 0 | 1 | 2;            // глубина погружения после шага
}
```

Три причины отказа — **рельеф** (глубокая вода), **уровень** (Δ ≥ +2 шагом, Δ ≤ −3) и **ребро**
(`CLIFF`, `WALL`) — проверяются в одном месте, поэтому «почему сюда нельзя» всегда один ответ.
Таблицы стоимостей и переходов — [`wiki/design/combat/terrain.md`](wiki/design/combat/terrain.md).

Пасфайндер — **Дейкстра по бюджету MP, не A\***: для подсветки достижимых клеток и для перебора
в ИИ нужно всё множество достижимого, а не один маршрут.

### 4.3 Линия видимости возвращает отчёт, а не `boolean`

`rules.md` требует модификатор рельефа к попаданию, `terrain.md` — счёт промежуточных лесных
гексов и учёт высот. Значит:

```ts
// core/map/los.ts
export interface LosResult {
  blocked: boolean;
  lightWoods: number;      // сколько редких лесов между стрелком и целью
  heavyWoods: number;
  partialCover: boolean;   // цель прикрыта возвышенностью частично
  levelAdvantage: number;  // разница уровней, стрелок минус цель
}
```

Уровень глаз — `elevation + 1` для стоящего робота; препятствие — `elevation + objHeight`;
блокировка определяется линейной интерполяцией высоты линии. Формула — в `terrain.md`.

**Ловушка:** линия между центрами гексов иногда идёт ровно по границе двух клеток. Правило
разрешения такой ничьей зафиксировано в `terrain.md` (выбирает стреляющий) и обязано быть
реализовано именно так. Иначе LOS выйдет несимметричным: A видит B, B не видит A. Обязателен
тест `los(a,b).blocked === los(b,a).blocked`.

**Кэш обязателен, а не «оптимизация потом».** Рельеф и высоты в бою почти не меняются, поэтому
`los(a, b)` считается один раз на пару клеток и запоминается; кэш сбрасывается только при
разрушении здания или изменении оверлея. Без него батч-симуляции из §5 не укладываются в
разумное время — расчёт там же.

### 4.4 Команды и события — размеченные объединения

```ts
// core/commands/types.ts
export type Command =
  | { kind: 'move';     unitId: UnitId; path: Hex[]; mode: MoveMode }
  | { kind: 'fire';     unitId: UnitId; weaponIdx: number; targetId: UnitId }
  | { kind: 'endPhase' };

export type BattleEvent =
  | { kind: 'moved';    unitId: UnitId; path: Hex[]; heatGained: number }
  | { kind: 'toHit';    attackerId: UnitId; targetId: UnitId;
                        need: number; roll: number; hit: boolean }
  | { kind: 'damaged';  unitId: UnitId; location: Location;
                        amount: number; armorLeft: number }
  | { kind: 'critical'; unitId: UnitId; slot: SlotRef }
  | { kind: 'fell';     unitId: UnitId; damage: number };

export type CommandResult =
  | { ok: true;  events: BattleEvent[] }
  | { ok: false; reason: RejectReason };
```

`switch` по `kind` проверяется компилятором на полноту вариантов — добавили событие, забыли
обработать, получили ошибку сборки.

**Событие `toHit` несёт и целевое число, и сам бросок.** Это бесплатно даёт боевой лог
(«PPC по цели: нужно 8, выпало 6 — промах»), а он делает бой понятным ещё до появления анимаций.

**Двухэтапность требует, чтобы событие несло и намерение, и итог.** Действие разрешается в два
шага — бросок и проверка исполнения, — поэтому у события есть поле `botched` с причиной срыва.
Без него журнал не сможет объяснить игроку, почему удавшееся попадание обернулось промахом, а
это прямое требование дизайна (правило 2 в `skills.md`). Проверка исполнения — одна функция
`rollExecution(pilot, situation)`, общая для стрельбы, движения, прыжка и рукопашной.

### 4.5 `enumerateLegalCommands` — с M2, а не когда понадобится ИИ

```ts
export function enumerateLegalCommands(state: BattleState, unitId: UnitId): Command[];
```

У этой функции три потребителя: интерфейс (что подсветить), ИИ из M5 (что перебирать), автобой из
M10 (то же самое). Если её нет с самого начала, ИИ обзаведётся собственной копией правил
валидации, и две копии разойдутся.

### 4.6 ГПСЧ

Четыре вопроса по порядку: зачем сид вообще, а не настоящая случайность; почему свой генератор,
а не библиотека; как это устроено; что это даёт на практике.

#### Зачем сид, а не `Math.random()` / `crypto.getRandomValues()`

Вопрос не «какую библиотеку взять», а более простой и более ранний: зачем вообще заводить сид,
если в JS уже есть встроенная случайность. Ответ — то, что весь раздел ниже называет «даёт
бесплатно», требует ровно одного свойства: **одинаковый вход (сид + список команд) обязан давать
одинаковый выход**. Настоящая случайность именно это свойство и уничтожает по определению — она
для того и нужна, чтобы не повторяться. С ней:

- **бой нельзя сохранить дешевле, чем видеозаписью** — состояние каждого броска пришлось бы
  писать отдельно, а не восстанавливать вычислением;
- **баг, пойманный один раз на десятитысячном автобое, нельзя переиграть** — он либо
  воспроизводится сразу тем же сидом и командами, либо не воспроизводится никогда;
- **результат батч-прогона баланса нельзя перепроверить** — второй запуск с «теми же» условиями
  на самом деле считает другую партию;
- **сетевой режим потребовал бы слать по сети каждый бросок**, а не команду игрока — на порядки
  больше трафика и рассинхрон при первой же потере пакета.

Сидированный ГПСЧ — не компромисс ради простоты реализации, а единственный способ получить
воспроизводимость в принципе. Настоящая случайность в проекте остаётся ровно там, где
воспроизводимость не нужна и даже мешала бы: игрок нажимает «🎲 случайный сид» и выбирает НОВУЮ
отправную точку — то есть `Math.random()` разрешён в двух конкретных местах интерфейса
(`ui/components/GeneratorControls.svelte`, `ui/App.svelte`), а не в правилах, и линтер следит,
чтобы больше нигде в `src/*.ts` он не появился (см. §4.7).

```ts
// core/rng/Rng.ts
export class Rng {
  private s: number;                        // ровно uint32
  constructor(seed: number) { this.s = seed >>> 0; }

  next(): number {                          // mulberry32
    this.s = (this.s + 0x6D2B79F5) | 0;
    let t = Math.imul(this.s ^ (this.s >>> 15), 1 | this.s);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  }

  d6(): number   { return 1 + Math.floor(this.next() * 6); }
  d2d6(): number { return this.d6() + this.d6(); }   // ДВА броска, не uniform(2..12)

  getState(): number  { return this.s; }
  setState(s: number) { this.s = s >>> 0; }
}
```

**Как это работает по шагам.** У боя есть один мастер-сид — обычное число. `RngSet` детерминированно
выводит из него по дочернему сиду на каждый именованный поток (`initiative`, `toHit`, …) — поэтому
поток `toHit` и поток `crits` дают несвязанные последовательности, даже разделяя один мастер-сид.
Каждый поток — это отдельный `Rng` из кода выше: вызов `.next()` по формуле mulberry32
детерминированно превращает текущее состояние `s` в следующее число `0…1` и в новое `s`. Какая
команда какой поток дёргает и сколько раз — решают ПРАВИЛА, а не порядок вызова откуда попало:
бросок на попадание всегда берёт ровно один `toHit`-ролл на выстрел, бросок зоны — один
`hitLocation`, и так для каждого правила. Из этого следует главное свойство: **один и тот же
мастер-сид плюс один и тот же список команд в том же порядке всегда трогает потоки в одной и той
же последовательности и получает одни и те же числа** — реплей и есть проверка этого свойства.

Три обязательных свойства, из-за которых берём своё, а не библиотеку:

1. **`d2d6` — сумма двух независимых d6.** Не `2 + floor(next()*11)`. Вся боевая математика
   BattleTech стоит на колоколе с пиком на 7; равномерное распределение сломает баланс полностью
   и незаметно.
2. **Состояние ГПСЧ входит в снапшот боя.** Иначе не работают ни сохранение в середине боя, ни
   реплей с середины.
3. **Именованные потоки** — `initiative`, `toHit`, `hitLocation`, `crits`, `piloting`, `skill`,
   `mapGen`, `campaign`; каждый со своим сидом, выведенным из мастер-сида. Иначе добавление
   одного нового броска в правила сдвигает всю последовательность, и все сохранённые тестовые
   бои разъезжаются при каждой правке правил.

   **ГПСЧ бота в этот набор не входит.** Размышления игрока — не состояние партии: пока бот
   бросал из общего набора, реплей по журналу команд не сходился, потому что команды
   воспроизводились, а поток ИИ оставался нетронутым. Бот получает свой `Rng`, выведенный из
   того же сида, но живущий в `sim/`.

   Поток `skill` обслуживает проверки исполнения (срыв) и броски на ранение пилота из
   [`wiki/design/pilots/skills.md`](wiki/design/pilots/skills.md) — они добавлены поверх боевых
   бросков и обязаны не сдвигать их последовательность.

#### Что это даёт на практике

Не абстрактная «воспроизводимость», а конкретные вещи, которыми проект уже пользуется:

- **Реплей — файл в несколько килобайт, а не видеозапись.** Сид + список нажатых команд
  восстанавливают двухчасовой бой кадр в кадр на любом компьютере.
- **Баг, пойманный один раз на десятитысячном автобое, воспроизводится точно.** Не нужно гоняться
  за условиями, при которых он «иногда» происходит — тот же сид и та же команда дают его снова.
- **Golden-replay — один тест на все регрессии детерминизма разом** (`test/replay.test.ts`): сид +
  журнал команд + хэш финального состояния; расхождение хэша значит, что где-то втихую поменялось
  правило или порядок бросков.
- **Батч-прогон баланса перепроверяем.** `pnpm sim --seeds 1..10000` даёт числа, которые второй
  прогон с теми же сидами обязан повторить — иначе замеру баланса нельзя верить вообще.
- **Задел под сетевой режим.** По сети имеет смысл передавать команды («пошёл на 0415»), а не
  результаты бросков — оба клиента посчитают одно и то же из одного сида.

#### Карта и бой — два мастер-сида, не один [добавлено 2026-08-28]

До этого момента вся партия — карта, бой, решения бота — выводилась из ОДНОГО мастер-сида:
`generateMap` строит рельеф из `RngSet(mapSeed)`, `makeBattle` считает бой из `RngSet(battleSeed)`,
бот в `sim/` берёт свой `Rng` от того же числа. Пока оба сида буквально совпадали, расхождения было
не видно нигде, кроме одного места: в интерфейсе бот детерминирован и на равных вводных всегда
выбирает один и тот же ход, поэтому «Автоход» на одном и том же сиде карты каждый раз воспроизводил
ОДИН И ТОТ ЖЕ бой — не только рельеф, но и каждое попадание/промах в тех же местах (сообщение
пользователя после четырёх одинаковых автобоёв подряд).

Сид карты и сид боя разделены: `ScenarioOptions.seed` (он же `MapDescriptor.seed`) — только
рельеф, биом, старты; `ScenarioOptions.battleSeed` (необязателен) — инициатива, попадания, зоны,
криты, пилотирование, срывы, броски бота. У них разные `RngSet`, и смена одного не трогает другой.
Интерфейс (`ui/state/battle.svelte.ts` → `GeneratorOptions.seed` / `.battleSeed`) держит их как два
отдельных поля: карта — фиксированный узнаваемый номер, который не меняется сам по себе (игрок
должен уметь вернуться на понравившуюся карту после перезагрузки страницы); бой — свежий при каждой
загрузке страницы и при каждом нажатии «⟳ Генерация» в шапке, которое карту не трогает.

**Обратная совместимость не сломана.** `battleSeed` необязателен и по умолчанию равен `seed` — для
батч-прогона (`pnpm sim`) и golden-replay ничего не изменилось: там один сид, как и раньше,
полностью определяет и карту, и бой целиком, что этим инструментам и требуется.

### 4.7 Детерминизм: чего не было в C# и что появляется в JS

- **Только целые числа в правилах.** Никаких накоплений с плавающей точкой в уроне и тепле.
  Деление — явный `Math.floor` / `Math.trunc`.
- **Порядок обхода — явный.** Никогда не полагаться на порядок ключей объекта или вставки в
  `Map`/`Set`. Списки юнитов перед обходом сортировать по `unitId`.
- **`Math.random` запрещён во всех `.ts`-файлах** правилом ESLint (`no-restricted-properties`,
  `eslint.config.js`, `files: ['**/*.ts']`) — одна строка конфига, охраняющая всю идею с сидом.
  Правило не покрывает `.svelte` (парсер для них в конфиге не заведён), и там есть ровно два
  сознательных исключения — там, где игрок явно просит новую отправную точку, а не там, где что-то
  решает ядро: `ui/components/GeneratorControls.svelte` (🎲 сид карты) и `ui/App.svelte`
  (перезапуск боя, §4.6). Дальше — те же именованные потоки, тот же детерминизм, никакой другой
  случайности в игре не остаётся.
- **Golden-replay тест** — сид + журнал команд + хэш финального состояния, проверяется в тестах.
  Один тест, ловящий все регрессии детерминизма разом. Заводится на M2.

## 5. Производительность: почему 10 000 боёв реально

Опасение «с ИИ тысячу симуляций быстро не прогонишь» справедливо для языковых моделей и
несправедливо для утилитарного бота ([`wiki/design/ai.md`](wiki/design/ai.md)). Расчёт:

| Величина | Оценка |
|---|---|
| Кандидатов на ход юнита | ~170 достижимых клеток × 6 фасингов ≈ **1000 позиций** |
| Вычислений на кандидата | ~32 прикидки попадания (своё оружие × враги + входящая угроза) |
| Дорогая часть | трассировка видимости |
| Бой **без** кэша видимости | ≈ 1 с |
| Бой **с** кэшем видимости | **50–100 мс** |
| 1000 боёв, один поток | 1–2 минуты |
| 1000 боёв, 8 worker-потоков Node | **10–15 секунд** |

Два рычага, если понадобится ещё быстрее:

1. **Выборка кандидатов** — оценивать не все 1000 позиций, а 30–50. Выборка берётся **из
   сидированного ГПСЧ**, поэтому прогон остаётся воспроизводимым.
2. **Понижение глубины** — в батч-режиме бот всегда играет на 1 ход, без просчёта ответа.

Оба рычага — параметры запуска `sim/`, не отдельный код.

## 6. Рендер боевой карты [уточнён в шаге 9a]

Три слоя, и это единственная нетривиальная часть отрисовки:

```
слой 0   рельеф             земля, обрывы, вода, дороги, массивы леса, горы, декор, сетка
слой 1   оверлеи и юниты    достижимость, линия огня, путь, фишки мехов, дымка
слой 2   обычный DOM/CSS    сайдбар, HUD, разбор целевого числа, кукла брони, журнал, радар
```

Слой 2 — ответ на «хочу неон и свечение»: `filter: drop-shadow()`, `box-shadow`, градиенты,
CSS-анимации пульсации. Всё это на DOM бесплатно и аппаратно ускорено.

**Слой 0 сейчас рисуется каждый кадр, а не в offscreen-канвас.** Прежний регламент требовал
рисовать рельеф один раз в отдельный канвас и дальше только копировать. С векторным видом
(шаг 9a §11) это перестало быть выигрышем: анимированы и вода, и дымка, а отсечение по камере
ограничивает стоимость кадра тем, что реально попало в окно.

**Что именно измерено, и чего замер НЕ показал.** Время кадра на 15×15, 24×24, 40×40 и 64×64 —
33.3 мс медиана и 34 мс на 95-м процентиле, одинаково на всех четырёх размерах. Это ровно 30 Гц,
то есть **упёрлось в частоту обновления браузера, а не в отрисовку**: кадр укладывается в бюджет
на всех размерах вплоть до оперативной карты, но насколько с запасом — этот замер не говорит.
Утверждать «держит 60 к/с на 64×64» по нему нельзя, и здесь этого не написано.

**Открытая цена решения:** отсечение по камере всё равно перебирает все клетки карты каждый
кадр — это линейный проход, и на потолке 100×100 он однажды станет заметен. Чанкование подложки
(16×16 гексов на чанк, LRU) заложено как следующий шаг и делается по замеру с отключённым
вертикальным синхронизмом, а не заранее и не по этому замеру.

Хит-тест по гексам — **не нужен сцен-граф**: попадание курсора в клетку это `pixelToHex(x, y)`,
чистая функция из `core/hex/`, которая всё равно требуется для других задач. Слой показа обязан
звать именно её: своя формула перевода разойдётся с картинкой на первом же изменении раскладки.

Пан и зум — матрица `ctx.translate` + `ctx.scale`, порядка 40 строк.

**Слой показа не считает правила.** Ни одного целевого числа, ни одной стоимости хода, ни одного
вердикта о перекрытии линии он не вычисляет: всё приходит готовым из ядра через `render/scene.ts`.
Это не стилистика, а найденная ошибка: в исходном макете перекрытие линии огня считалось прямо в
рисовании, и условие было ложно всегда — луч не краснел ни разу. Второй источник истины опасен не
тем, что спорит с ядром, а тем, что молча не работает.

**Фильтр знания живёт в одном месте.** `render/scene.ts` переводит `BattleState` в то, что видно,
и применяет уровень контакта: по засветке — метка без класса и без чисел, по силуэту — класс без
брони и тепла, по опознанной — полный лист. Если бы карта фильтровала сама, а панель сама, они
разошлись бы на первом же исключении, и игрок узнавал бы из подписи то, чего разведка ему не
давала.

Звёздная карта не требует ни force-directed раскладки, ни D3: у систем Внутренней Сферы есть
канонические координаты, а рёбра-маршруты выводятся из радиуса прыжка. Это фиксированное облако
точек с тем же canvas и той же камерой; для хит-теста на сотнях систем — простой сеточный индекс.

## 7. Интерфейсный слой

Svelte 5. Экраны глобального слоя (кланы, контракты, ангар, звёздная карта, боевой HUD) —
обычные компоненты: `<script>` + разметка + `<style>` со scope'ом.

- **Библиотеку UI-компонентов не подключаем.** MUI/AntD/PrimeVue — это админ-панели; в
  BattleTech они дадут вид бухгалтерской программы, и с их стилями придётся бороться. CSS тут
  пишется свой в любом случае.
- **Отдельный стейт-менеджер не нужен.** Состояние кампании — обычный объект из `core/`,
  руны Svelte просто на него подписываются. `core/` про Svelte не знает.
- Локализация с первого дня. Термины BattleTech каноничны по-английски, интерфейс русский — без
  словаря это потом не расшить. Устройство после шага 52:
  - **два словаря**: экраны — `t('ключ')` из `ui/i18n/<язык>.json`; ядро — ключи и параметры, в
    слова их превращает `tr()` из `core/log/<язык>.json` (термины, причины, журнал боя `log.*`,
    текстовый отчёт `report.*`). Причины и замечания ядро отдаёт **данными** (вид + id + числа:
    `RefitBlocker`, `AssemblyIssue`, `RefitIssue`, `RepairNote`), фразу собирает экран;
  - **русский текст в коде запрещён тестом** `test/i18n-hardcoded.test.ts`: разбор TS и Svelte, без
    комментариев и диагностики разработчика (`throw`, проверки схем, `console`). Файл исключений
    `test/i18n-allowlist.json` пуст и может только сокращаться (`pnpm i18n:allowlist`). Id, уже
    записанные в сохранения, помечаются `i18n-ignore` с причиной;
  - **язык — настройка игрока, двумя пунктами**: язык интерфейса и язык терминов (`weapon.*`,
    `equipment.*`) — экран «Настройки», выбор в `localStorage` (`platform/preferences.ts`), не в
    сохранении. Смена языка пересобирает экраны (`App.svelte`, `{#key}`); на хеш боя и сохранения
    язык не влияет;
  - **формы и форматы — от языка**: множественное число `tn()` по CLDR (`Intl.PluralRules`), месяцы и
    порядок даты — в словаре, разделитель разрядов — таблицей по языку;
  - **имена собственные не переводятся**: пулы имён и позывные по умолчанию — `data/names.json`;
  - фразы с выделенным словом — одной строкой словаря с плейсхолдером (`tParts` на экранах, тон
    куска `LogPart` в журнале), не кусками «до» и «после»; рендер словаря не знает и получает
    подписи набором `RenderLabels`.

## 8. Данные

- Все числа — в JSON в `game/data/`, не в коде. Правится без пересборки, генерируется скриптами.
- **Каждая таблица имеет Zod-схему.** Схема — единственный источник и валидации, и TS-типа
  (`z.infer`). Без неё опечатка `"damage": "10"` вместо `10` всплывёт через месяц как загадка,
  а с ней загрузка падает сразу с внятным сообщением.
- **Валидатор корректности шасси** — `validateChassis()`: бюджет тоннажа (реактор + каркас +
  броня + вооружение + охладители ≤ тоннаж) и бюджет слотов. Комбинаторная система из
  [`wiki/design/mechs/classification.md`](wiki/design/mechs/classification.md) порождает тысячи
  вариаций; без валидатора генератор выдаст горы нежизнеспособных машин. Это главный
  содержательный риск проекта — важнее любого выбора библиотеки.

Сохранения:

- **Сохранение — снапшот состояния**, не журнал команд.
- **Реплей — сид + журнал команд**, и он действителен только для той версии правил, при которой
  записан. В файл пишется `rulesVersion`; при несовпадении реплей отказывается проигрываться,
  а не врёт.

## 9. Хранилище и упаковка в приложение

Доступ к файлам изолирован одним интерфейсом — это то, что позволяет игре одновременно быть и
сайтом, и приложением:

```ts
// platform/Storage.ts
export interface Storage {
  save(slot: string, data: Uint8Array): Promise<void>;
  load(slot: string): Promise<Uint8Array | null>;
  list(): Promise<string[]>;
}
// IndexedDbStorage — браузер, и это единственная реализация
```

`core/` про `platform/` не знает вовсе. Vitest ничего не замечает.

**Поставка — сайт** (решение 2026-09-02, `wiki/decisions.md`). Десктопная упаковка в Tauri снята:
не надо подгонять сборки под платформы и держать тулчейн Rust, обновления мгновенные. Интерфейс
`Storage` от этого не меняется — он и заводился ради того, чтобы ядро не знало, куда пишут байты.

Что из этого следует и о чём нельзя забыть:

1. **Сохранение живёт в IndexedDB браузера** и пропадает вместе с очисткой данных сайта. Поэтому
   у игрока есть экспорт и импорт файла сохранения (главное меню, страница роты): снимок
   сериализуется в JSON и проходит схему.
2. **Разные браузеры рисуют по-разному.** Safari (WKWebView), Chrome и Firefox расходятся в
   CSS-фильтрах, шрифтах и мелочах canvas. Проверять на трёх, а не на одном.
3. **Квота на хранилище** у IndexedDB не бесконечна и в приватном окне может быть нулевой. Отказ
   записи игрок обязан увидеть, а не потерять кампанию молча.

## 10. Автоматические проверки границ

Архитектура держится не дисциплиной, а конфигом:

| Правило | Чем обеспечено |
|---|---|
| `core/` не знает о показе | ESLint `no-restricted-imports` в `src/core/**`: запрет `svelte`, `@tauri-apps/*`, а также `zone: ui/render/platform` |

| Данные валидны | Zod при загрузке + отдельный тест «все JSON проходят схемы» |

## 11. Художественный регламент [пересмотрен в шаге 9a]

**Вид проекта — векторная тактическая карта, а не пиксель-арт.** Это смена курса, и её надо
читать целиком, а не по строчке.

Прежний регламент выбирал пиксель-арт как ответ на главную проблему разработки без художника —
несогласованность ассетов: жёсткая палитра делает согласованность автоматической, низкое
разрешение делает ассет дешёвым. Рассуждение было верным, но у него нашёлся ответ дешевле.
Пользователь собрал тактический макет целиком на векторной графике Canvas 2D — органические
массивы леса со сглаженным контуром, реки сплайнами, зубцы обрывов, горы с гранями, фишки мехов
шести силуэтов, — и утвердил его как вид проекта (2026-08-27). Ассетов у этого вида **ноль**:
каждая фигура — код. Значит и несогласовывать нечего.

| Параметр | Значение |
|---|---|
| Ориентация гекса | **острокрышая** (pointy-top), ряды со смещением через ряд, odd-r |
| Гекс при масштабе 1× | 64 × 74 px (ширина между гранями × высота между вершинами) |
| Палитра | один файл `game/data/palette.json`: интерфейс + шесть биомов + три схемы показа |
| Масштабирование | плавное, 0.2×…3×. Сглаживание включено: вектор его требует |
| Фасинги робота | шесть, поворотом контекста. Спрайтов нет — крутить нечего |
| Декор | детерминирован от сида клетки: та же карта на том же сиде даёт те же деревья |

**Почему ориентация сменилась.** Настольные планшеты BattleTech плоскокрыши, и до шага 9a ядро
было таким же. Макет нарисован на острокрыших гексах, и выбор между «перерисовать утверждённый
вид» и «повернуть геометрию ядра» пользователь сделал в пользу второго. Цена оказалась мала:
шесть аксиальных векторов направлений те же самые, сменились только их имена (N/NE/SE/S/SW/NW →
NW/NE/E/SE/SW/W), проекция в пиксели и нумерация клеток (odd-q → odd-r). Движение, видимость,
рёбра и фасинг не изменились ни на строку — тесты это подтвердили сразу.

**Что осталось от прежнего регламента без изменений:** палитра одним файлом и правило «ничего
вне него» для цветов карты. Разметка на Svelte несёт те же значения цветов в своих блоках
`style` — так они были написаны в макете, и переписывать их в переменные значило бы менять вид,
а не место хранения.

Общий вид: векторная карта, поверх — резкий современный интерфейс на HTML/CSS с моношрифтом и
мягким свечением. Ориентиры по читаемости 2D-тактики прежние — Into the Breach («всегда понятно,
что произойдёт») и Battle Brothers.

**Растр разрешён узко и идёт ДВУМЯ УРОВНЯМИ** (решение 2026-09-01, уточнено шагами 48 и 50). Правило
прежнее: только стационарные изображения, которые не несут состояния — портреты пилотов, диски
планет, эмблемы, голограммы миссий, силуэты шасси. Всё, что показывает состояние машины, рисуется
кодом.

| Уровень | Что это | Кто скачивает |
|---|---|---|
| **Атлас** | одна сетка, все ячейки набора, ячейка под самый крупный показ В СПИСКАХ | все и всегда, одной загрузкой |
| **Одиночный файл** | та же ячейка в натуральном разрешении, по файлу на ячейку | только тот игрок, который щёлкнул именно по этой картинке |

Второй уровень заведён шагом 48 и нужен там, где на картинку смотрят вблизи: атлас платит за все
свои ячейки сразу, поэтому поднять в нём разрешение под один крупный взгляд — значит утяжелить
загрузку всем. Обратное правило тоже держится: **вверх картинка не растягивается никогда**, потолок
задаёт исходник.

**У портретов мехов атласа нет (шаг 50).** У каждого рисунка несколько раскрасок фракций, и атлас
заставил бы качать все машины одной раскраски ради трёх на экране. Поэтому у мехов оба уровня —
отдельные WebP: квадрат 256 px под списки (`<рисунок>/<раскраска>-s.webp`, ~17 КБ) и 900 px во весь
рост под крупный показ (`-l.webp`, ~140 КБ), оба с ленивой загрузкой. При запуске игры не грузится
ни одной картинки меха.

Атласы пишет офлайн-паковщик `tools/pack_ui_atlases.py`, геометрию — в `ui/components/atlases.json`.
Портреты мехов — `tools/pack_mech_art.py` из исходников `_tmp/Meches`: раскладка по классам и список
нарисованных раскрасок — в `ui/components/mechArt.json`, реестр раскрасок и их связь с фракциями —
`game/data/paints.json`. Сгенерированное руками не правится.

**Если позже появится художник**, тайлсет ложится поверх той же структуры без переписывания
генератора: он строит данные, а не картинки.

## 13. Правила, чтобы проект не встал

1. Каждый этап заканчивается коммитом с тегом. Тесты красные — этап не закрыт.
2. `core/` всегда покрыт тестами. `render/` и `ui/` — ручная проверка.
3. Числа в JSON, каждая таблица со схемой.
4. Не начинать следующий этап, пока предыдущий не играется.
5. Раз в этап — сыграть целиком как игрок и записать, что раздражает.
6. Делегировать вспомогательному агенту можно: JSON-таблицы, генерацию вариаций шасси, шаблонные Zod-схемы,
   пакетные переименования, спрайтовые заготовки. **Не делегировать:** правила боя, LOS, ИИ,
   архитектуру команд, ГПСЧ, сериализацию, `platform/`.

## 14. Масштабируемость: что заложено сразу

Принцип: закладывать запас там, где он **бесплатен сегодня** и дорог завтра; не закладывать там,
где он усложняет код ради гипотезы.

### Заложено с самого начала (ничего не стоит)

| Что | Как | Что это даёт потом |
|---|---|---|
| Уровни клеток | знаковый байт (−128…+127), правила ограничивают −5…+5 | расширить диапазон = правка правил |
| Признаки рёбер | битовая маска, занято 5 из 8 бит | ещё 3 типа рёбер без смены формата |
| Рельеф и оверлей | `Uint8Array`, до 256 значений каждый | новые типы местности и эффектов свободно |
| Размер карты | нигде не зашит, приходит из данных | карты M11 крупнее боевых — без правок |
| Фракции, оружие, шасси, личности ботов, веса, пороги репутации | JSON + Zod-схема | контент добавляется без пересборки и генерируется скриптами |
| Матрица отношений фракций | `Int8Array(n × n)` | сотни фракций так же дёшевы, как десяток |
| Тексты | `t()` + словарь с первого дня | второй язык = второй JSON |
| Команды и события | размеченные объединения | новое действие — новый вариант, компилятор найдёт все места |
| Глобальный слой | те же `Command` → `Event`, что и бой | кампания реплеится и тестируется как бой; журнал репутации получается бесплатно |
| Сохранения | `rulesVersion` в файле | правила меняются, старые сейвы не врут |
| Сид | именованные потоки | новый бросок в правилах не сдвигает остальные |
| Тяжёлые расчёты | ядро чистое, без DOM | перенос в Web Worker — вопрос обёртки, не переписывания |

### Сознательно не закладываем

| Что | Почему |
|---|---|
| Сетевой мультиплеер | архитектура «сид + журнал команд» это допускает, но удваивает объём тестирования. Возможность сохраняется, работа откладывается |
| 3D | направление закрыто: 3D-контента нет и не планируется (`wiki/decisions.md` §1) |
| Модовый API | нужен стабильный формат данных, которого ещё нет |
| Бесконечные / потоковые карты | пошаговому бою не нужны |
| Своя система частиц | Pixi добавляется отдельным слоем, если вообще понадобится |
